# Pair Agent P0.5：共享对话与 Agent 通信设计

> **状态：**会话设计已确认，等待文档 review
>
> **日期：**2026-08-31
>
> **定位：**P0.5 位于 Phase 0 运行骨架与 P1 权限/并发之间，补齐 Session-to-Pair Bridge、Pair Session Events 可视化、被动共享上下文和显式 Agent-to-Agent 通信。

## 1. 目标与边界

P0.5 解决 Phase 0 中已经存在 Pair Ledger 与 Shared Context Builder，但 Navigator/Pilot 的普通会话输出没有进入 Pair Ledger 的断层。

完成后必须满足：

- 用户与任一 Agent 的公开对话可以成为 Pair Session Event；
- Navigator 与 Pilot 的普通回答进入共同上下文，但不自动唤醒另一 Agent；
- 另一 Agent 在下一次 Turn 构造请求时一次性获得新增 Pair Events；
- Navigator 与 Pilot 可以通过受控 Peer Message 主动通信，且该通信必须唤醒接收方；
- 用户可以随时查看 Pair Session Events 的语义视图和完整审计视图；
- 两条 DSH Agent Session 仍然独立，Pair Request 不直接读取另一 Agent 的 Local Session。

P0.5 不提前实现 P1 的 Goal-impact 判断、权限矩阵、Revision fencing 和 Pause/Resume/Cancel，也不提前实现 P2 的完整 delivery crash-window 对账、workflow、Sub-agent 和 ArtifactRef 聚合。

## 2. 核心语义

### 2.1 Pair Ledger 是共同上下文的唯一权威来源

每个 Agent 请求由以下部分构成：

```text
全部 Pair Session Shared Events
  + 当前 Agent 的 Local History
  - 已被 Pair Event 完整表达的本地重复消息
  + 当前 Agent 尚未提升到 Pair Ledger 的本地消息
```

Request Builder 不扫描另一条 Agent Session。另一 Agent 的公开内容必须先由 Session-to-Pair Bridge 提升为 Pair Event，才能进入当前 Agent 的 Shared Context。

### 2.2 被动共享不等于主动唤醒

| 输入或输出 | Pair Event | Channel | 是否唤醒另一 Agent |
| --- | --- | --- | --- |
| 用户发送给 Navigator | `user.message` | `navigator` | 只唤醒 Navigator |
| 用户发送给 Pilot | `user.message` | `pilot` | 只唤醒 Pilot |
| Agent 普通公开回答 | `agent.message` | 发送者角色 | 否 |
| 显式 Peer Message | `agent.message` | 接收者角色 | 是 |
| Pilot Turn 失败 | `agent.turn_failed` | `navigator` | 是 |
| Navigator 分派 Task | `task.assigned` | `shared-control` | 唤醒 Pilot |

普通共享消息只推进 Pair Ledger。另一 Agent 在自己的下一次 Turn 读取最新 Shared Head。只有显式 Peer Message、Task Assignment 或后续 P1 控制事件才产生定向 delivery。

## 3. 总体架构

```text
Navigator DSH Session ─┐
                       ├─ session/event ─> Session-to-Pair Bridge
Pilot DSH Session ─────┘                       │
                                              │ flush + durable read
                                              ▼
                                         Pair Ledger
                                              │
                         ┌────────────────────┴───────────────────┐
                         ▼                                        ▼
                 Pair Events UI                         Pair Context Builder
                                                                  │
                                                     Agent 下一 Turn 消费
```

Pair Runtime 在 DSH 公共 Context 上安装一个 Host-owned Bridge。Bridge 使用公开的 `session/event` hook 观察两个固定顶层 Session，并严格按 Pair Registry 中的 Session binding 过滤。DSH core 和通用 `agent/request-layout` seam 不引入 Pair 类型。

## 4. Pair Event 设计

### 4.1 普通 Agent 回答

普通回答复用现有 `agent.message`：

```ts
{
  type: "agent.message",
  actor: { kind: "agent", role: "navigator" },
  source: "navigator-session",
  channel: "navigator",
  visibility: "shared",
  authority: "navigator",
  refs: {
    sourceEventIds: [
      "dsh:<sessionId>:<sessionEventSeq>:agent.message"
    ]
  },
  payload: {
    schemaVersion: 1,
    kind: "turn-output",
    text: "...",
    content: [{ type: "text", text: "..." }],
    completion: "complete",
    origin: {
      sessionId: "pair:<pairId>:navigator",
      sessionEventSeq: 42,
      turn: 3,
      messageId: "..."
    }
  }
}
```

`channel` 等于发送者角色表示普通公开输出。`visibility=shared` 使其进入双方下一次请求，但 Bridge 不调用另一 Agent 的 `followup`。

### 4.2 显式 Peer Message

两个角色共享模型可见工具：

```ts
pair_message_peer({
  text: string,
  expectsReply?: boolean,
  replyTo?: string
})
```

发送者从 DSH `ToolRunContext.agent.id` 与 Pair binding 推导；接收者固定为另一角色。模型不能提供 `senderRole`、`receiverRole`、`sessionId`、`wake` 或 `expectedLedgerHead`。

Peer Message 仍使用 `agent.message`，但 `channel` 指向接收者，`payload.kind="peer-message"`。因此：

```text
actor.role === channel  → 普通回答，不主动唤醒
actor.role !== channel  → Peer Message，必须投递并唤醒 channel 对应 Agent
```

工具执行必须先 append + flush Pair Event，再调用接收方 `followup`。显式 Peer Message 不把本地 tool-call/tool-result span 标为 `representation=full`，因为它不能替代发送方的完整本地工具协议。

Peer Message 采用固定的 fail-closed 上限，避免两个 Agent 在没有用户输入的情况下无限互相唤醒：

- `text` 去除首尾空白后必须非空，且最多 `64 KiB` UTF-8；
- 每个发送方 Turn 最多成功发送一条 Peer Message；
- 请求者对当前用户回答所需的有限问题设置 `expectsReply=true`；接收者必须以 `replyTo=<请求 Pair Event ID>` 发送关联回复，不能只在本地频道回答；
- `replyTo` 必须指向当前 Turn 收到的唯一一条 `expectsReply=true` canonical Peer Event，回复本身不能再次设置 `expectsReply=true`；
- 持续委派工作不使用请求—回复字段，仍使用 completion-specific turn-end handoff；
- 每条 Peer Message 记录稳定 `causalRootId` 和 `hop`；接收方继续发送时沿用 root 并令 `hop + 1`；
- P0.5 固定 `maxPeerHops=4`；超限返回工具错误，不 append、不投递；
- 同一发送 Turn 的并发或重复调用由 Host 以 Session/Turn identity 串行判定，只有第一条可以成功。

`causalRootId` 和 `hop` 由 Host 从当前 Turn 的 durable input provenance 推导：

- 用户消息、Task 或其他非 Peer delivery 启动的 Turn 创建新 root，root 使用对应 `pairEventId`；原生 composer Turn 使用稳定 `dsh:<sessionId>:<turn>` root；
- Peer delivery 的 plugin source 携带 Host 生成的 `causalRootId` 与当前 `hop`；接收 Turn 沿用该 root；
- Tool 执行从 `ToolRunContext.agent.id` 找到准确 Session，再从该 Session 当前 open Turn 的输入来源恢复 causal context；模型参数不参与；
- 一个 Turn 如果领取了多个不同 Peer roots，则本 Turn 的 `pair_message_peer` fail closed，不猜测应该延续哪条因果链；
- Peer Event 与 delivery trigger 持久保存 root/hop，因此重试和恢复可以重建相同判定。

### 4.3 Session Event Link

Bridge 为被 Pair Event 完整表达的普通用户消息和 Agent 回答追加 `session_event.linked(visibility=infrastructure)`：

```ts
{
  schemaVersion: 1,
  sessionId: string,
  fromSessionSeq: number,
  throughSessionSeq: number,
  messageIds: string[],
  pairEventId: string,
  representation: "full" | "summary" | "artifact-ref",
  representedContentDigest?: `sha256:${string}`
}
```

`fromSessionSeq..throughSessionSeq` 是 durable derivation range，可以从被表示的消息延伸到确认其最终性的 `step/end`、`turn/end`；`messageIds` 只列出这个范围内被 Pair Event 表示的消息。Projector 校验范围内的 Local History 消息边界与 `messageIds` 精确一致，因此允许尾部非消息事件，但不允许夹带未声明消息。

历史 Local History 只根据持久 link 排除重复项。当前输入允许两种严格、request-local 的例外证明：

- Pair delivery 的 DSH `user/message.source` 已携带 Host 生成的 `pairEventId` 与 `deliveryId`，Request Builder 可以验证它与 durable Pair Event 一致，并生成 request-local provenance link；
- 原生 composer 的当前 `source.kind="user"` 消息如果已经被 Bridge 提升为 Pair Event、但 persistent link 尚未写入，Request Builder 可以用 Pair Event 中的稳定 DSH source ID、origin 和规范化 payload 与当前本地消息做完全等价校验，等价时生成 request-local link；不等价时 fail closed。

Request-local link 只避免 Shared Events 与 Local History 重复。Current Trigger 继续表达调度原因，但只能携带 `kind`、`pairEventId`、`deliveryId`、causal root/hop 等引用，不再复制已经存在于 Shared Event 中的用户文本或 Task 内容。Bridge 在 flush 后补写持久 link；后续请求不再依赖临时证明。

Bridge 只有在 Pair Event 对原始规范化消息形成完整、可逆表达时才写 `representation="full"`。P0.5 对纯 text-block 消息保存完整 `content` block 数组，可以使用 `full`；如果原消息还包含显式 reasoning、非文本 block 或其他未提升内容，只保存用户可见文本并写 `representation="summary"`。新 summary link 必须只表示一条消息，并保存按 `pair-represented-content/v1` 规范化后计算的 `representedContentDigest`。Projector 先校验 Session、message ID、origin、actor/source/channel，再比较本地 text blocks 与 Pair Event 内容摘要；全部一致时只删除 text block，保留 reasoning 和非文本 block。相同文本出现在另一条消息中不会被去重；缺少 digest、digest 不一致、跨消息、协议相关或无法证明安全的 span 均完整保留。显式 Peer Message 不为 tool-call span 创建 `full` link。

## 5. Session-to-Pair Bridge

### 5.1 Hook 与最终回答边界

`session/event` 是 canonical Session log 的 post-commit、fire-and-forget feed。Hook 只做校验与轻量入队，不在同步 listener 内执行 I/O。

Bridge 按 Turn 收集 `user/message`、`assistant/message` 与 `turn/end`：

- 用户消息只要 durable 就可以共享，即使该 Turn 最终失败；
- `assistant/message` 可能只是包含 tool call 的中间 Step；
- `turn/end.reason=completed` 时，只选择该 Turn 最后一条自身不包含任何 `tool-call` block、且包含公开文本的 assistant message，记为 `completion="complete"`；
- `turn/end.reason=max-tokens` 时，只有最后一条 assistant message 自身不含 tool call 且包含公开文本才可记为 `completion="partial"`；
- `blocked`、`error`、`aborted` 和 `interrupted` 不从更早的工具步骤回捞 assistant message；Session dispose 表现为 `aborted`，其嵌套原因可以是 `disposed`；
- `error` 会派生唯一的 `agent.turn_failed`；其中保存失败角色、Turn、错误码、有界错误消息和原始 Session event 位置。Pilot 失败在事件 durable 后，以只含 Pair Event 引用的 delivery 唤醒 Navigator；Navigator 自身失败只进入共同事件，不自我唤醒；
- reasoning、chunk、tool-call 中间消息、普通 tool result 和隐藏 Chain of Thought 不提升为共同对话。

`user/message` 必须按 source allowlist 处理：

- `source.kind="user"`：原生 composer 的真实用户输入，触发 coalesced durable drain，并可派生共享 `user.message`；
- `source.kind="plugin"` 且 plugin 为 Pair delivery：已有 Pair Event，只补 request-local/persistent link；Peer delivery 同样只建立来源关联；
- bootstrap、普通 plugin inject、Goal continuation、skill、compaction 和其他 Harness 内部输入保持 Agent-local，不得提升为用户共同事实；
- 未识别 source fail closed，不猜测它是否代表用户。

### 5.2 Durable drain

Navigator 与 Pilot 各自拥有一个串行 drain worker：

```text
allowed user/message or turn/end marks session dirty
  → await sessions.flush(session)
  → sessionPersistence.readFrom(sessionId, nextSeq)
  → derive Pair Events in Session seq order
  → append Pair Ledger
  → publish new Ledger Head
```

`session/event` 只表示内存提交；只有 `session/flush` 成功并从 persistence 读回的连续事件才可以派生 Pair Events。用户输入可以在长 Turn 完成前通过 coalesced drain 进入 Pair Ledger；最终 Agent 回答仍必须等待匹配的 `turn/end`。

### 5.3 Pair delivery 与原生 composer

- Pair Host 的 `Send through Pair` 输入先写 `user.message`，再投递目标 Agent。Bridge 识别 delivery source 中的 `pairEventId`，只补 link，不重复创建用户事件。
- 原生 DSH composer 的用户输入没有既有 Pair Event。Bridge 在该 `user/message` flush 并读回后补写共享 `user.message` 和 link，不必等待整个 Turn 结束，也不唤醒另一个 Agent。

## 6. 幂等、恢复与关闭

### 6.1 幂等

派生记录使用稳定来源 ID：

```text
dsh:<sessionId>:<sessionEventSeq>:user.message
dsh:<sessionId>:<sessionEventSeq>:agent.message
dsh:<sessionId>:<sessionEventSeq>:agent.turn_failed
dsh:<sessionId>:<sessionEventSeq>:session_event.linked
```

追加前在 Pair mutation lock 内检查 `refs.sourceEventIds`。如果来源 ID 已存在，必须比较已有记录与期望派生记录的规范化 type、actor、source、channel、refs 和 payload：完全等价才视为幂等成功；任何不等价冲突都 fail closed。CAS 冲突后 replay 并重新判断。

### 6.2 两阶段写入

普通回答需要先写 `agent.message`，再写 `session_event.linked`。如果进程在两者之间退出：

- message 与 link 都没有：恢复时依次补写；
- message 已有、link 缺失：只补 link；
- 两者都有：跳过；
- link 存在但 message 缺失：视为损坏并 fail closed。

Link 缺失期间，Local History Projector 保留本地消息，保证信息不丢失。

### 6.3 P0.5 恢复策略

正常运行使用两个内存 `nextSessionSeq` 增量读取。恢复时不信任内存 cursor：

1. 先安装 Bridge hook；
2. 恢复两条 DSH Session；
3. flush Session；
4. 扫描两条 durable Session log；
5. 从 Pair Ledger 构建已有来源 ID 索引；
6. 幂等补写缺少的 message/link；
7. catch-up 完成后才接受新输入。

当两条 Session 同时存在缺失记录时，恢复先按每个 DSH source event 组成不可拆分的派生组：represented `user.message` / `agent.message` 固定在组内 ordinal `0`，对应 `session_event.linked` 固定为 ordinal `1`。派生组再按 `(event.time, roleOrder, sessionEventSeq)` 稳定排序，`roleOrder` 固定为 Navigator 在前、Pilot 在后。这样 link 永远不会先于 represented message，同一组 durable logs 的重复恢复也会产生相同补写顺序。

P0.5 会话较短，允许恢复时全量扫描。持久 cursor、Shared Checkpoint 和长会话增量恢复优化后置到 P2。

### 6.4 正常关闭

```text
Pair Host 停止新输入
  → 两个 Agent 到达安全边界
  → flush DSH Sessions
  → Bridge final drain
  → 移除 hook
  → 关闭 DSH Runtime
```

完整 delivery append/wake crash-window 重投递仍属于 P2。

## 7. Pair Session Events API 与 UI

### 7.1 查询 API

新增独立接口，不复用当前返回 Pair Projection 的 SSE `/events`：

```http
GET /api/pairs/:pairId/session-events
  ?afterSeq=0
  &limit=100
  &view=semantic|all
```

```ts
interface ListPairSessionEventsResponse {
  pairId: string;
  throughLedgerHead: number;
  sharedHead: number;
  events: PairEvent[];
  nextAfterSeq: number;
  hasMore: boolean;
}
```

`afterSeq` 是 Pair Ledger 物理序号。默认 `semantic` 展示用户、Agent、Goal、Task、控制和 Artifact 等语义事件；`all` 额外展示 Request Snapshot、link 与 delivery lifecycle。Cursor 必须穿过被过滤事件，不能产生分页缺口。

### 7.2 Events 抽屉

Pair Header 增加 `Session Events` 入口，打开右侧抽屉：

- Semantic 与 All/Audit 切换；
- 按 Pair seq 展示时间、type、actor、source、channel 和 visibility；
- 显示可读摘要，并允许展开原始 JSON；
- JSON 只作为文本渲染；
- 初始分页加载；现有 Projection SSE 发现 `ledgerHead` 前进后，使用 `nextAfterSeq` 拉取 tail；
- 即使 SSE 合并中间 Projection，也通过 Ledger API 补回所有事件。

### 7.3 Pair-level 输入

Navigator/Pilot Pane 标题区各增加 `Send through Pair` 输入，复用现有角色消息 API：

- 使用当前 `ledgerHead` CAS；
- 成功后清空草稿；
- 409 时保留草稿并等待 Projection 更新后重试；
- `pending` 表示“已保存，等待投递”，不能显示为消息丢失。

原生 DSH composer 继续保留，并明确标注其用户消息在对应 `user/message` durable 后同步、Agent 最终回答在 `turn/end` durable 后同步。P0.5 不新增强制改道原生 composer 的 DSH Web seam。

## 8. 验收标准

P0.5 至少证明：

1. 用户与 Navigator 多轮聊天时，每条共享用户消息和 Navigator 最终公开回答进入 Pair Events；
2. 普通聊天不会创建 Pilot Turn；
3. Pilot 下一次 Turn 的 Provider Request 包含新增 Navigator 对话，且只出现一次；
4. Navigator 调用 `pair_message_peer` 后，Peer Event 先 durable，Pilot 随后产生新 Turn；
5. Pilot 到 Navigator 的反向路径完全对称；
6. 模型不能伪造 sender、receiver 或 Session ID；
7. 同一 DSH source 经 hook 重入、CAS 冲突和重启扫描只生成一次 Pair Event/link；
8. Semantic 视图隐藏 infrastructure events，All/Audit 展示完整 Ledger；
9. Pair 输入 CAS 冲突不会丢失草稿；
10. 同一 Shared Head 的公共请求前缀仍保持一致；另一 Agent 的内容只来自 Pair Events，不直接读取对方 Local Session。
11. `expectsReply` Peer request 只能由指向其 Pair Event ID 的 `replyTo` Peer message 满足，错误或不相关引用 fail closed；
12. Pilot Turn 失败会生成唯一 `agent.turn_failed` 并以引用唤醒 Navigator，且不会把旧 assistant step 误当最终回答；
13. 通过 identity 与 `representedContentDigest` 双重证明的单消息 summary link，其已共享可见文本不在 Provider Local History 重复发送，reasoning/非文本 block 仍保留；相同正文的其他消息、摘要不一致和范围内存在额外消息边界时不去重。

测试采用 TDD，至少覆盖 Contracts/Store、Bridge、Coordinator/Adapter、Pair Host API、Pair Web UI 和 capture-provider E2E。实现完成后运行 Pair workspace 全量验证与固定 DSH 回归。

## 9. 延后能力

下列能力不阻塞 P0.5：

- 持久化 per-Agent unread cursor（P2）；
- Shared Checkpoint 与长会话恢复优化；
- Events 全文搜索、导出、高级筛选和 token/chunk 流式展示；
- 自动总结大体积工具输出与 ArtifactRef；
- 强制所有原生 DSH composer 输入先经过 Pair Host；
- 自动判断普通对话是否影响 Goal/Task；
- delivery append 与 wake 之间崩溃后的 exactly-once 重投递；
- 多进程 Bridge 和分布式事件订阅。

P1 在此基础上实现 Goal/Task/Execution Plan 权限、纠偏升级、Revision fencing 和 Pause/Resume/Cancel；P2 完成 delivery 对账、恢复 continuation、workflow、Sub-agent、ArtifactRef 与故障注入。
